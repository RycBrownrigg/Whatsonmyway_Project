<objective>
Turn a populated pack into a versioned, downloadable artifact: select every eligible POI, refuse
the build when a required framework field is missing anywhere, snapshot the membership, write the
pack file, checksum it, and cut a version — with an inline report the admin can act on when it
fails.

Purpose: ADMINBUILD-01 is the phase's terminal capability and the ROADMAP's stated goal — "from an
empty catalog to a build-ready standard pack". It is also the hand-off to Phase 2, which downloads
exactly this file.
Output: `api/src/services/packBuild.ts`, `POST /v1/admin/packs/:id/build`, and the Build Pack panel
on the pack detail page.
</objective>

  <name>Task 1: Choose the on-disk pack file format</name>
  <read_first>
    - `Product Specification.md` §5 lines 245-304 (the on-device SQLite model the pack file must populate: `installed_packs`, `pack_field_defs`, `pack_filter_defs`, `pois`)
    - `Product Specification.md` §13 (Versioning & Migration Strategy) and §4 lines 182-193 (`pack_versions.format_version` — "on-device pack FILE format; app refuses formats it doesn't understand")
    - `.planning/phases/01-admin-pack-authoring-build/SKELETON.md` (Out of Scope — the download endpoint and on-device migrations are Phases 2 and 5)
  </read_first>
  <decision>
    What is the on-disk format of a built pack file — the bytes Phase 2 downloads, Phase 5 version-guards, and every future pack is written in?
  </decision>
  <context>
    This is a one-way door. `pack_versions.format_version` exists precisely because changing this
    format later means shipping a new format version, keeping the old reader alive in the app, and
    migrating or re-cutting every pack already in circulation. Phases 2, 4, 5 and 6 all read
    whatever is chosen here. The spec fixes the on-device *schema* (§5) but never states the *file*
    format, so this is genuinely open and must be decided before any build code is written.
  </context>
  <options>
    A) **Gzipped JSON document** — `pack-{slug}-v{n}.json.gz`, a single UTF-8 JSON object with
       `format_version`, a `pack` block, `field_defs`, `filter_defs`, and a `pois` array ordered by
       id.
       Pros: no new server dependency (`node:zlib` is built in); the client owns its own SQLite
       schema and migrations, which is exactly what Phase 5 needs; human-diffable when
       decompressed, so a bad build is debuggable; trivially versioned by the top-level
       `format_version` key.
       Cons: the client inserts rows on install rather than dropping a file into place, so install
       time grows with pack size.
       *Recommended.*

    B) **Pre-built SQLite database file** matching §5 exactly, gzipped — the client copies it into
       place.
       Pros: fastest install; zero client-side transform.
       Cons: the server must write SQLite, which means either the experimental `node:sqlite`
       module or a native `better-sqlite3` dependency (a new package needing its own legitimacy
       check and a native build in the `wowm-api` container); and it puts the on-device schema
       under the server's control, which collides head-on with Phase 5's on-device migration
       story.

    C) **Uncompressed JSON** — the same document as A without gzip.
       Pros: simplest possible writer and reader.
       Cons: several times the download size over a metered mobile connection for no benefit;
       spec §3 lists resumable ranged downloads precisely because pack files are expected to be
       large.
  </options>
  <recommendation>
    Option A. It keeps the API dependency-free, leaves on-device schema ownership with the client
    where Phase 5 needs it, and makes a bad build inspectable. If B is chosen instead, the package
    legitimacy gate must be re-run for `better-sqlite3` before it is installed.
  </recommendation>
  <acceptance_criteria>
    - A human has selected exactly one option and the selection is recorded in the plan summary.
    - If option B is selected, a package-legitimacy verification for the chosen SQLite package is completed before any install.
  </acceptance_criteria>
  <resume-signal>Reply with "A", "B", or "C", or describe a different format.</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /v1/admin/packs/:id/build` | Triggers a filesystem write and a multi-table transaction |
| `packs.slug` → filesystem path under `PACK_FILE_DIR` | An admin-supplied string becomes part of a write path |
| Generated pack file → future clients | These bytes become authoritative POI data on every user's device from Phase 2 onward |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-19 | Tampering | pack file path construction in `api/src/services/packBuild.ts` | high | mitigate | The path segment comes from `packs.slug`, which `CreatePackSchema` constrains to `^[a-z0-9][a-z0-9-]{0,62}$` — no dots, no separators, so no traversal is expressible. The service additionally resolves the final path and asserts it stays inside the resolved `PACK_FILE_DIR` before writing. |
| T-01-20 | Tampering | `pack_pois` rewrite + `pack_versions` insert | high | mitigate | Snapshot delete, snapshot insert, version insert and `current_version` update run inside a single Drizzle transaction, so an interrupted build cannot leave a pack pointing at a version whose membership was half-written. Validation runs to completion before the transaction opens. |
| T-01-21 | Tampering | build eligibility query | high | mitigate | Eligibility is a server-side predicate over `geocodeStatus` and `status`; the request body carries no POI list, so a caller cannot smuggle an ungeocoded or archived POI into a pack. |
| T-01-03 | Tampering | `api/src/services/packBuild.ts` | high | mitigate | Drizzle query builder only, including the snapshot rewrite; no interpolated SQL on the build path. |
| T-01-22 | Information Disclosure | generated files under `PACK_FILE_DIR` | medium | mitigate | `packfiles/` is gitignored so pack contents never enter the repository, and the directory is not served by any route in this phase — Phase 2 adds the entitlement-gated download endpoint. |
| T-01-23 | Denial of Service | build over a large POI set | medium | accept | A build loads every eligible POI into memory to serialise it. At Phase 1 volumes (manual entry, a single admin) this is bounded by hand. Revisit with Phase 6's bulk import, which is where pack sizes become large enough to need streaming. |
| T-01-01 | Spoofing | `registerBuildRoutes` | critical | mitigate | Registered only inside `registerAdminRoutes`, inheriting the shared-token preHandler. |
</threat_model>
