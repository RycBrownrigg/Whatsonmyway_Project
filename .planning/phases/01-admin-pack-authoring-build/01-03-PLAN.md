    - `normalizeAddressKey` lowercases, collapses runs of whitespace, and strips punctuation from street + city + state + ZIP, so two spellings of the same address produce the same key.
    - Zero candidates returned: status `failed`, latitude and longitude null, confidence null, errorCode `ADDRESS_NOT_FOUND`.
    - Two or more candidates returned: status `low_confidence`, latitude and longitude null, errorCode `ADDRESS_AMBIGUOUS`, candidates array populated with one entry per candidate.
    - One candidate with `dpv_match_code` Y and rooftop-grade precision: confidence 1.0, status `ok`.
    - One candidate scoring exactly at the configured threshold: status `ok` — the comparison is `>=`, so the boundary belongs to `ok`.
    - One candidate scoring just below the threshold: status `low_confidence`, errorCode `LOW_CONFIDENCE_MATCH`, coordinates still stored because a single match was returned.
    - One candidate with `dpv_match_code` N: status `failed`, errorCode `ADDRESS_NOT_FOUND`, coordinates null.
    - A non-2xx HTTP response or an aborted request retries twice with backoff, and only then returns status `failed` with errorCode `PROVIDER_ERROR`.
    - A malformed provider payload (missing metadata, non-numeric latitude) is treated as `PROVIDER_ERROR`, never written through as a coordinate.

    `geocodeAddress` issues one GET to the Smarty US Street Address API host with query params
    `auth-id`, `auth-token`, `street`, `city`, `state`, `zipcode`, `candidates=10`, using
    `AbortSignal.timeout(5000)`. Read the credentials from `process.env.SMARTY_AUTH_ID` and
    `process.env.SMARTY_AUTH_TOKEN`; throw an `AppError` naming the missing variable when either
    is unset. Before writing the request, confirm the current parameter names, the response
    envelope, and the `analysis.dpv_match_code` / `metadata.precision` / `metadata.latitude` /
    `metadata.longitude` field names against Smarty's current US Street Address API reference —
    do not rely on recalled field names.

    Parse the response with a Zod schema before touching any value, so a malformed payload becomes
    `PROVIDER_ERROR` rather than a bad coordinate in the database. Then map it:
      - HTTP non-2xx, abort, or Zod parse failure: retry the request up to two more times with
        250ms then 1000ms backoff; if all attempts fail return status `failed`, errorCode
        `PROVIDER_ERROR`, coordinates null. §15 says surface to the admin only once retries are
        exhausted, and this is where that is honoured.
      - Zero candidates: status `failed`, errorCode `ADDRESS_NOT_FOUND`, coordinates null.
      - Two or more candidates: status `low_confidence`, errorCode `ADDRESS_AMBIGUOUS`,
        coordinates null, `candidates` populated from every returned candidate. Never select one.
      - Exactly one candidate: score it into a 0-1 `confidence` — `dpv_match_code` of `Y` with
        rooftop-grade precision scores 1.0; `Y` with block-grade precision scores 0.8; a `S` or
        `D` match code (secondary address dropped or missing) scores 0.5; ZIP-centroid-grade
        precision scores 0.3; `N` scores 0.0. Read the threshold from
        `process.env.GEOCODE_CONFIDENCE_THRESHOLD` with a default of 0.7. A confidence of 0.0
        returns status `failed` with `ADDRESS_NOT_FOUND`. Otherwise, when `confidence` is greater
        than or equal to the threshold the status is `ok`; when it is strictly less the status is
        `low_confidence` with errorCode `LOW_CONFIDENCE_MATCH`. The comparison is deliberately
        inclusive on the `ok` side so a score exactly at the threshold is accepted. Coordinates
        come from the single candidate in both of those cases.

    Add `GEOCODE_CONFIDENCE_THRESHOLD=0.7` to `api/.env.example` beside the Smarty credentials.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /v1/admin/pois` | Untrusted POI payload including arbitrary `custom_fields` / `filter_values` object keys |
| API → Smarty US Street Address API | Outbound address data plus API credentials; inbound untrusted JSON |
| Smarty response → PostgreSQL | Provider-supplied coordinates and candidate objects become stored JSONB |
| `api/.env` → process | Provider credentials at rest |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Information Disclosure | `SMARTY_AUTH_ID` / `SMARTY_AUTH_TOKEN` | high | mitigate | Credentials are read only inside `api/src/services/geocoding.ts` from `process.env`; the admin client never receives them. A negative grep over `admin/app`, `admin/lib` and `admin/components` gates the build. Credentials travel as query params to the provider, so the adapter must never log the request URL. |
| T-01-06 | Tampering | Smarty response handling in `geocodeAddress` | high | mitigate | The provider payload is Zod-parsed before any value is read; a malformed payload becomes `PROVIDER_ERROR` and nothing is persisted, so provider-controlled JSON can never land unvalidated in `pois.geocode_candidates`. |
| T-01-03 | Tampering | `api/src/routes/admin/pois.ts` | high | mitigate | Drizzle query builder only; `customFields` and `filterValues` are Zod-parsed records written as JSONB parameters, never interpolated into SQL. |
| T-01-07 | Denial of Service | `geocodeAddress` | medium | mitigate | `AbortSignal.timeout(5000)` bounds every call and retries are capped at two with 250ms/1000ms backoff, so a hung or rate-limited provider cannot pin an admin request open indefinitely. |
| T-01-14 | Tampering | `customFields` / `filterValues` object keys | medium | mitigate | Keys are constrained upstream by the framework `^[a-z][a-z0-9_]{0,63}$` regex (plan 01-02); this route additionally rejects any submitted key that does not match a saved field or filter definition for the pack. |
| T-01-15 | Information Disclosure | Fastify request log on the POI route | low | accept | POI addresses are business data the admin typed, and the log stays on the VPS behind the existing nginx/ufw/fail2ban perimeter (`Product Specification.md` §3). No end-user PII is involved; revisit if admin logs are ever shipped off-box. |
| T-01-SC | Tampering | shadcn component installs (`badge`, `textarea`, `switch`) | high | mitigate | Pulled by the `shadcn` CLI already verified in plan 01-01's blocking-human legitimacy checkpoint; no new npm package is introduced by this plan. |
